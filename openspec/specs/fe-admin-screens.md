# Spec: FE admin screens

## Requirements

Schedule clock (2026-10-03): the live admin app uses the current Asia/Manila date,
not the mock fixture clock. `/schedule` initially shows the current period and
Today re-reads the clock when clicked, including after midnight in an open tab.
Month/week/day navigation uses that same date. Only Storybook freezes time to
match its demo data.

Customer directory registration (2026-10-03): `/customers` and `/customers/[customerId]`
include only accounts registered through the customer portal (`apps/web`, port 9000),
recorded by `profiles.customerRegisteredAt`. A shared Auth/profile row, staff invite,
password reset, or phone-number edit does not make an account a customer. Customers
who later become staff remain in the customer directory. Registration eligibility
applies server-side before search, filters, counts, and pagination; a staff-only
profile requested through customer detail returns not found. This marker is not an
authorization role and does not replace staff permissions or customer ownership checks.

1. Admin lives in `apps/admin` (port 9001). Runtime screens read data through the React Query factories in `apps/admin/src/lib/query/`, which use typed `@balanse/api-client` functions. Server prefetch uses the server client. Storybook supplies mock-backed fetchers; runtime screens do not import fixture files or call Supabase directly.
2. Route inventory: `/login`; `/dashboard`; `/schedule`, `/schedule/new` (desktop intercept `@modal`), `/schedule/duplicate`, `/schedule/requests`, `/schedule/[sessionId]`, `/schedule/[sessionId]/change`, `/schedule/[sessionId]/recurrence`, and `/schedule/[sessionId]/event`; `/students` and `/students/[customerId]` for the built-in Coach role; `/events`, `/events/new`, and `/events/[eventId]`; `/bookings` and `/bookings/[bookingId]`; `/payments`, `/payment-qr`, `/cancellations`, and `/reschedules`; `/customers` and `/customers/[customerId]`; `/coaches` and `/coaches/[coachId]`; `/classes`, `/classes/new` (desktop intercept `@modal`), and `/classes/[classId]`; `/venues` and `/venues/[venueId]`; `/bundles` and `/bundles/[bundleId]`; `/staff`, `/staff/[staffId]`, `/staff/roles`, `/staff/roles/new`, and `/staff/roles/[roleId]`; `/sales`, `/transactions`, `/reports`, `/reports/[sessionId]`, and `/marketing-insights`; `/sessions/[sessionId]/roster`; `/settings` with content and policy subroutes; `/my-profile`. Dev-only: `/dev/kit`, `/dev/tokens`.
3. Admin nav is the `ADMIN_NAV_ITEMS` list (Dashboard, Schedule, Events, Bookings, Payments, Payment QR, Cancellations, Reschedules, Customers, Coaches, Classes, Venues, Bundles, Sales, Transactions, Reports, Marketing insights, Staff, Settings), plus the contextual Coach-only `My Students` destination. The collapsible shell groups them as Operations / Directory / Studio; My Students follows Schedule when present; Events sits in Operations immediately after Schedule; Venues sits in Directory after Classes; Bundles sits in Directory; Reports precedes Marketing insights and Staff. `/schedule/[sessionId]/event` highlights Schedule, the same way `/sessions/[sessionId]/roster` does. `/events`, `/events/new`, and `/events/[eventId]` highlight Events; `/venues/[venueId]` highlights Venues. The shell renders the inline collapsible sidebar from 1024px (`lg`) and a top bar with a navigation drawer below that, so a regular iPad in portrait (768–834px) keeps the full content width; the collapsed icon rail is a pointer affordance (hover tooltips), not a tablet default. The sidebar is not rendered in `apps/web`.
4. Login is email/password only. Copy includes the administrator help line. There is no sign-up, no forgot-password, and no Google button on admin.
5. Coach rates, coach cost, and financial report figures require the matching sensitive permissions from `@balanse/domain` (`openspec/specs/staff-roles-and-permissions.md`). Query keys are rooted at `["admin", adminAuthScope(principal)]` with a staff authorization fingerprint (#296). Public/customer types and `apps/web` never receive rate or cost fields.
6. Shared composition: `AdminPageShell` (title, breadcrumb, actions, stats, tabs); `AdminDataTable` for lists (a table when its container fits it, cards when the container is narrower than 1024px (64rem) or the table would scroll sideways — measured on the container, not the viewport, because the sidebar changes the content width); `AdminQueueList` + `AdminQueueCard` for payments/cancellations/reschedules; `AdminWizard` for class create/edit; a one-page session composer for session create/edit (dialog on the schedule, full screen on phones, routed page on hard navigation) with class and coach tiles, time-slot chips, venue cards, an inline weekly repeat, and a live summary with a date preview and coach/venue clash warnings; `AdminPageTabs` for coach and settings; `@balanse/ui` field family + admin form kit for write forms.
7. Forms use `react-hook-form` + `zodResolver`. Schema and `defaultValues` are colocated with form components or under `modules/admin/forms/` for shared form contracts. Constraints derive from `@balanse/domain` `FIELD_CONSTRAINTS`. Validation/server errors surface through `FieldError` / `FormMessage`. Writes go through typed query mutations and `notify.admin`. Photo and GCash QR uploads follow the signed-intent API contract; Storybook may simulate upload states.
8. Per-route `loading.tsx` files render the matching page-skeleton shell. The dashboard segment has one shared `error.tsx`; routes do not carry custom error copy.
9. Storybook retains the mock harness. `MockRuntimeOptions` knobs include `latencyMs`, `failNext`, `failPublicSessions`, `sessionBecameFullId`, `failProofUpload`, `emptyAdminQueues`, `failFinalCredit`, and `emptyPackageCatalogue`. Queue fixtures include generated rows (`buildGeneratedQueueBookings` in `packages/mock`).
10. Bundle catalogue, grant, and paid-acquisition review live under `/bundles/**`, `/customers/[customerId]`, and `/payments`. They use the package API/query layer; entitlement and ledger rules are in `openspec/specs/session-bundles.md`.
11. Event list (`/events`) and detail (`/events/[eventId]`) read the typed event API through the admin query layer. The authoring form lives at `/schedule/[sessionId]/event`, with a session picker at `/events/new`. Its zod schema and defaults are colocated on that form and use the admin form kit, query mutations, and `notify.admin`. The form is an event-specific step composer (Session → Story → Look → Logistics → Review; Session is skipped when the route binds one) with a live customer preview card. Create validates each step before moving on and ends with Save as draft or Save and publish (offered only when the session is published). Edit opens any step; publish, cancel and archive sit in the page header. Access uses `events.read` / `events.manage` (`openspec/specs/events.md`).

12. Sales (`/sales`) sits under Studio before Reports and is exclusive to active Super Admin staff. Both navigation and direct route access use the shared `superAdminOnly` requirement; custom roles cannot gain access through sales-report permissions. Server prefetch checks access before loading any report data. The screen provides date-range controls, sales/refund/net totals, paid-booking count, daily sales, class mix, and searchable class/session sales tables with session-report links. Report dates refer to session dates, not payment settlement dates.

13. Transactions (`/transactions`) sits under Studio after Sales and uses the same active-Super-Admin-only nav and route requirement, including a check before server prefetch. It reads bookings, package acquisitions, and customer names through scoped queries. The responsive table shows separate booking payment/refund records and paid self-purchase package records, with search, type/status/method filters, source links, and all-record received/refunded/net/pending summaries. Package credit redemptions, free claims, grants, and unpaid waitlist entries are excluded. Only completed records affect received/refunded/net totals. Dates explicitly show source creation time because booking settlement/refund timestamps are unavailable; the screen is a current-state financial history, not an immutable transaction-event ledger.
14. Schedule (`/schedule`) exposes a visible `Your classes` scope for staff with a linked coach profile. The built-in Coach role defaults to this scope and can only see its assigned sessions; staff with both a coach profile and all-schedule access may switch between `All classes` and `Your classes`. Staff without a linked coach profile retain the all-schedule default and do not receive an inapplicable scope control.
15. A cancelled booking detail (`/bookings/:bookingId` where status is `CANCELLED`) is a closed record: it leads with cancellation status and booking context, omits active-booking actions, and exposes refund state and completion only to actors with the corresponding refund permissions.
16. `/settings` remains the sole admin settings destination and retains its existing granular section permissions. `/my-profile` is available to every active staff actor, including custom roles with no other route permission. The account menu always exposes My profile and exposes Studio settings only when permitted. Profile notification preferences remain mock-only session controls and do not call `/api/*`.
17. Coach class change requests (#337, WIRE-E20). A coach never cancels a class on their own. The coach assigned to an upcoming session (without `schedule.cancel`) sees **Can't make it?** in the schedule panel with three paths — **Reschedule** (new date + start time, same length), **Find a substitute** (pick an active coach; clash flagged), or **Request cancellation** (last resort) — each with a reason, at `/schedule/[sessionId]/change`. One pending request per class; the coach can withdraw it. Admin / Super Admin review at `/schedule/requests` (also in the header inbox and as a notice in the schedule panel): approve applies the change (move the session, swap the coach on the session and its bookings, or cancel the session), deny requires a note and keeps the class. Approving needs the permission that would make the change directly — `schedule.cancel` for cancellations, `schedule.update` for reschedule / substitute — and nobody reviews their own request. No new permission keys. Runtime reads and writes use the coach-scoped API; Storybook retains mock fixtures.
18. `My Students` is a contextual built-in-Coach-only workspace at `/students` and `/students/[customerId]`. It reads only the signed-in coach's sessions through the coach-scoped API, which derives the linked coach id from the authenticated staff actor; all other roles, including Super Admin, are denied. The list separates students with an upcoming booking from students with recorded attendance. Detail shows only the coach's own session history, session-attendance count, next booking, and contribution: verified/cash booking or consumed-package class value attributable to that coach's classes. It is not studio-wide sales, payroll, or profit; detail onboarding omits referral and heard-from attribution.

19. Table/list date filters (#342): `/bookings` (inclusive session dates), `/events` (inclusive event session dates), and the shared sales overview used by `/reports` and `/sales` render the existing `@balanse/ui` `DateRangePicker`. They support presets, typing, keyboard selection, mobile display, and clear range. Clearing an operational list filter shows all dates; clearing the report range queries all report dates. `/schedule` uses its calendar view rather than a table range filter; `/transactions` currently has no date filter.
20. Staff lookup on `/bookings`, `/payments`, `/cancellations`, and `/reschedules` uses the existing plain-text customer booking reference (`BWH-…`) as one stable tracking ID across all four surfaces. It is visible on each booking row or queue card and the booking detail, and staff can search by reference or customer name. Queue search filters before cursor pagination so a reference can find a record beyond the loaded page; counts and empty states reflect the search. No separate payment or request identifier is invented for these booking-backed mock records.

21. The schedule sidebar shows a selected-day hourly timeline in Philippine time, with overlapping sessions in separate lanes and a live current-time line for today. A session crossing midnight appears on both calendar dates; the next day shows and labels only its after-midnight portion. Clicking that continuation opens the next day's details. Clicking a session opens its details over the timeline; Back to day restores the scroll position, and previous/next navigate the day's sessions. Staff with `schedule.update` can move future, non-cancelled sessions to another start time on their start day using a drag grip or keyboard arrows in 15-minute steps; continuation segments have no move grip. A review shows old/new times, affected booked places and waitlist count where roster access permits, and coach/venue overlaps before saving. Moves preserve duration and bookings, including when the end falls on the next day, and affect only one recurrence occurrence. Started sessions and destinations in the past are blocked; the API checks the original window under the session lock to reject stale moves.
