# Spec: FE admin screens

## Requirements

1. Admin lives in `apps/admin` (port 9001). Screens read data only through the React Query factories in `apps/admin/src/lib/query/`, which call `getMockAdapter()`. Screens do not `fetch` `/api/*` and do not import fixture files.
2. Route inventory after the polish wave: `/login`; `/dashboard`; `/schedule`, `/schedule/new` (desktop intercept `@modal`), `/schedule/duplicate`, `/schedule/[sessionId]/recurrence`, and `/schedule/[sessionId]/event`; `/students` and `/students/[customerId]` for the built-in Coach role; `/events`, `/events/new`, and `/events/[eventId]`; `/bookings` and `/bookings/[bookingId]`; `/payments`; `/cancellations`; `/reschedules`; `/customers` and `/customers/[customerId]`; `/coaches` and `/coaches/[coachId]` plus `/coaches/new`; `/classes` and `/classes/[classId]` plus `/classes/new` (desktop intercept `@modal`); `/venues` (create and edit in a dialog); `/bundles` and `/bundles/[bundleId]` plus `/bundles/new`; `/staff` and `/staff/[staffId]`; `/staff/roles`, `/staff/roles/new`, and `/staff/roles/[roleId]`; `/sales`; `/transactions`; `/reports` and `/reports/[sessionId]`; `/sessions/[sessionId]/roster`; `/settings`; `/my-profile`. Dev-only: `/dev/kit`, `/dev/tokens`.
3. Admin nav is the `ADMIN_NAV_ITEMS` list (Dashboard, Schedule, Events, Bookings, Payments, Payment QR, Cancellations, Reschedules, Customers, Coaches, Classes, Venues, Bundles, Sales, Transactions, Reports, Staff, Settings), plus the contextual Coach-only `My Students` destination. The collapsible shell groups them as Operations / Directory / Studio; My Students follows Schedule when present; Events sits in Operations immediately after Schedule; Venues sits in Directory after Classes; Bundles sits in Directory; Reports remains between Bundles and Staff in the catalog. `/schedule/[sessionId]/event` highlights Schedule, the same way `/sessions/[sessionId]/roster` does. `/events`, `/events/new`, and `/events/[eventId]` highlight Events. The sidebar is not rendered in `apps/web`.
4. Login is email/password only. Copy includes the administrator help line. There is no sign-up, no forgot-password, and no Google button on admin.
5. Coach rates, coach cost, and financial report figures require the matching sensitive permissions from `@balanse/domain` (`openspec/specs/staff-roles-and-permissions.md`). Query keys are rooted at `["admin", adminAuthScope(principal)]` with a staff authorization fingerprint (#296). Public/customer types and `apps/web` never receive rate or cost fields.
6. Shared composition: `AdminPageShell` (title, breadcrumb, actions, stats, tabs); `AdminDataTable` for lists; `AdminQueueList` + `AdminQueueCard` for payments/cancellations/reschedules; `AdminWizard` for class create/edit; a one-page session composer for session create/edit (dialog on the schedule, full screen on phones, routed page on hard navigation) with class and coach tiles, time-slot chips, venue cards, an inline weekly repeat, and a live summary with a date preview and coach/venue clash warnings; `AdminPageTabs` for coach and settings; `@balanse/ui` field family + admin form kit for write forms.
7. Forms use `react-hook-form` + `zodResolver`. Schema and `defaultValues` are colocated under `modules/admin/forms/`. Constraints derive from `@balanse/domain` `FIELD_CONSTRAINTS`. Validation/server errors surface through `FieldError` / `FormMessage`. Writes go through `lib/query/mutations.ts` and `notify.admin` on the redesigned surfaces. Photo and GCash QR still use `MockImageUpload` (pending keys, no Storage).
8. Per-route `loading.tsx` files render the matching page-skeleton shell. The dashboard segment has one shared `error.tsx`; routes do not carry custom error copy.
9. Mock harness remains on. `MockRuntimeOptions` knobs are `latencyMs`, `failNext`, `failPublicSessions`, `sessionBecameFullId`, `failProofUpload`, `emptyAdminQueues`, plus BE-058 `failFinalCredit` and `emptyPackageCatalogue`. Queue fixtures include ~120 generated rows (`buildGeneratedQueueBookings` in `packages/mock`).
10. Bundle catalogue / grant / paid-acquisition review screens are FE follow-up for #290. Domain types and `MockDataAdapter` methods already exist (`getAdminBundles`, `grantAdminPackage`, …).
11. Event list (`/events`) and detail (`/events/[eventId]`) read `getMockAdapter()` through the admin query layer. The authoring form lives at `/schedule/[sessionId]/event`, with a session picker at `/events/new`. Its zod schema and defaults are colocated on that form and still use the admin form kit, `lib/query/mutations.ts`, and `notify.admin`. The form is an event-specific step composer (Session → Story → Look → Logistics → Review; Session is skipped when the route binds one) with a live customer preview card, not `AdminWizard`. Create validates each step before moving on and ends with Save as draft or Save and publish (create, then the existing publish mutation; offered only when the session is published). Edit opens any step, and publish, cancel, and archive sit in the page header. Nav, `events.read` / `events.manage`, and adapter methods are in place (`openspec/specs/events.md`). Screens do not call `/api/admin/events`.

12. Sales (`/sales`) sits under Studio before Reports and is exclusive to active Super Admin staff. Both navigation and direct route access use the shared `superAdminOnly` requirement; custom roles cannot gain access through sales-report permissions. Server prefetch checks access before loading any report data. The mock screen provides date-range controls, sales/refund/net totals, paid-booking count, daily sales, class mix, and searchable class/session sales tables with session-report links. Report dates refer to session dates, not payment settlement dates.

13. Transactions (`/transactions`) sits under Studio after Sales and uses the same active-Super-Admin-only nav and route requirement, including a check before server prefetch. It reads bookings, package acquisitions, and customer names through scoped mock queries. The responsive table shows separate booking payment/refund records and paid self-purchase package records, with search, type/status/method filters, source links, and all-record received/refunded/net/pending summaries. Package credit redemptions, free claims, grants, and unpaid waitlist entries are excluded. Only completed records affect received/refunded/net totals. Dates explicitly show source creation time because booking settlement/refund timestamps are unavailable; the screen is a current-state financial history, not an immutable transaction-event ledger.
14. Schedule (`/schedule`) exposes a visible `Your classes` scope for staff with a linked coach profile. The built-in Coach role defaults to this scope and can only see its assigned sessions; staff with both a coach profile and all-schedule access may switch between `All classes` and `Your classes`. Staff without a linked coach profile retain the all-schedule default and do not receive an inapplicable scope control.
15. A cancelled booking detail (`/bookings/:bookingId` where status is `CANCELLED`) is a closed record: it leads with cancellation status and booking context, omits active-booking actions, and exposes refund state and completion only to actors with the corresponding refund permissions.
16. `/settings` remains the sole admin settings destination and retains its existing granular section permissions. `/my-profile` is available to every active staff actor, including custom roles with no other route permission. The account menu always exposes My profile and exposes Studio settings only when permitted. Profile notification preferences remain mock-only session controls and do not call `/api/*`.
17. Coach class change requests (#337). A coach never cancels a class on their own. The coach assigned to an upcoming session (without `schedule.cancel`) sees **Can't make it?** in the schedule panel with three paths — **Reschedule** (new date + start time, same length), **Find a substitute** (pick an active coach; clash flagged), or **Request cancellation** (last resort) — each with a reason, at `/schedule/[sessionId]/change`. One pending request per class; the coach can withdraw it. Admin / Super Admin review at `/schedule/requests` (also in the header inbox and as a notice in the schedule panel): approve applies the change (move the session, swap the coach on the session and its bookings, or cancel the session), deny requires a note and keeps the class. Approving needs the permission that would make the change directly — `schedule.cancel` for cancellations, `schedule.update` for reschedule / substitute — and nobody reviews their own request. No new permission keys; mock-only, BE contracts are backlog.
18. `My Students` is a contextual built-in-Coach-only workspace at `/students` and `/students/[customerId]`. It reads only the signed-in coach's sessions through coach-scoped mock adapter methods; all other roles, including Super Admin, are denied. The list separates students with an upcoming booking from students with recorded attendance. Detail shows only the coach's own session history, session-attendance count, next booking, and mock contribution: paid booking or consumed-package class value attributable to that coach's classes. It is not studio-wide sales, payroll, or profit, and has no `/api/*` or database wiring.
